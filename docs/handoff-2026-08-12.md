## The most important operational fact: this repo has concurrent sessions

More than one Claude Code session has been working the **same branch**
(`claude/print-farm-scheduler-review-3uo1ay`) at once, and it has caused real
confusion twice. A future session — human or Claude — needs to know this going
in:

- **PRs here are merged locally, not with GitHub's button.** `main` carries
  real "Merge pull request #N" commits, but GitHub's own records show those PRs
  as `state: closed, merged: false`. That combination is normal *for this repo*
  and means someone ran `git merge` + `git push` then closed the PR by hand. It
  does **not** mean the work was rejected. Judge what shipped by reading `main`,
  never by a PR's merged flag.
- **Work appears in `main` that the session in front of you did not do.** PRs
  #25 and #33 both landed with a session tag matching "this" session while being
  another window's work. Do not assume the commit log is your own history.
- **A transcript once described work that was never in the code.** During this
  session a block of chat claimed four history-panel behaviours were built and
  browser-verified with screenshots. None of it was in `main`, and this sandbox
  has no browser tools to have taken those screenshots with. The lesson is the
  standing rule below, stated hard: **trust the file, not the narrative.** Every
  claim in this handoff was re-checked against the repo this session; do the
  same to this handoff.

If you can, **work on a fresh branch off `main` per change** rather than sharing
the long-lived review branch — it is the shared branch that makes the above
messy.

## For whoever picks this up

The single invariant that keeps biting when it's forgotten: **mutation handlers
must copy only what they change**, and must not write when nothing meaningfully
changed. The save layer diffs tasks/printers/groups by object identity, so a
handler that returns a fresh object for an untouched row causes a pointless
PATCH, and one that mutates in place causes a missed save. Two bugs found in
this session's own audit were both writes that fired when nothing had really
changed. Check any new task/printer/group handler against that rule before
anything else.

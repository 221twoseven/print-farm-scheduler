## Audit findings

Everything in this section was found by auditing this session's own output. All
of it is **fixed** unless marked otherwise.

### Bugs

**1. `completedAt` was re-stamped on a no-op status change.** `updateTask`
stamped the completion time whenever a patch contained `status`, without
checking that the status had actually *changed*. The task context menu lists
every status including the one already set, so re-picking **Complete** on an
already-finished job rewrote its completion time to the present — and PATCHed
the row to record that the job finished at the moment somebody opened a menu.
Now guarded on an actual transition (`patch.status !== t.status`).

**2. Dropping a staging job back onto staging PATCHed the whole staging list for
no visible effect.** Once item 22 made staging order fully computed, `moveTask`
moving a task to the end of the array became invisible — but it still shuffled
array position and re-ran `reindex`, renumbering every staging row after the old
position, i.e. one PATCH per row. With ~50 staged jobs, one stray drag could
rewrite most of the list while appearing to do nothing. `moveTask` now returns
early when a staging job is dropped on staging. Printer queues are deliberately
left alone: they still order by `sortOrder`, so dropping a job on its own
printer legitimately sends it to the back of that queue.

Neither bug could destroy data — the first rewrites one timestamp, the second
rewrites `SortOrder` values that nothing in staging reads — but both wrote to
SharePoint when nothing had meaningfully changed, which is exactly what the save
layer's no-op suppression exists to prevent.

### Robustness and elegance

**3. Sort keys could return `NaN` into the comparator.** `Date.parse` on a
malformed stored value returns `NaN`, and `NaN !== NaN` is true, so a bad row
reached `return na - nb` and returned `NaN` from the comparator — formally
undefined behaviour for `Array.prototype.sort`. Both keys now route through a
`timeKey()` helper that treats unparseable as absent (`Infinity`, sorting last),
so a bad row sorts to the bottom instead of corrupting the ordering around it.

**4. `formatTimestamp()` ran six times per detail-modal render** — twice in the
visibility condition and twice more per stamp in the body, each one a fresh
`new Date()` plus `toLocaleString()`. Hoisted to two consts.

### Stale comments and docs

**5. `architecture.md` still described staging's old sort** ("`sortOrder` as the
stable tiebreaker inside a tier") while `decisions.md` and `ui-reference.md`
described the new one. Two docs in the repo directly contradicted each other —
worse than either being merely out of date. Fixed, and the section now also
records that `sortOrder` is still carried and reindexed for the save layer even
though nothing reads it for display in staging.

**6. `ui-reference.md`'s designer-view table still listed "Dragging within
staging to reorder"** as an available capability. It isn't, in either view, as

**7. `architecture.md`'s state-model task shape was missing seven fields** —

session's `createdAt` and `completedAt`. Five of those predate this session
(they landed in #10, #11 and #23), so this was pre-existing drift that this
session added to rather than caused.

**8. `architecture.md`'s layout table had drifted up to ~140 lines** and the
file's stated length was still "~4,500 lines" against an actual ~4,700.
Refreshed using the greppable section-banner recipe the file itself documents.

**9. A comment above the staging filter still read "stable within a tier."**
Reworded to name the real sort.

**10. `data-model.md` overstated `sortOrder`'s role in staging.** This session
first wrote that it was "the final tiebreaker" there, which isn't quite true —

| Question | Built as | Where |

  as a blank board) is ruled out.
- The staging comparator and the `updateTask` stamp logic were **extracted from
  the file as source text and executed** against table-driven cases: tier

`checkSchema()` accepts the two new columns against the real lists, which is the

## For whoever picks this up

The single most load-bearing thing to keep in mind when touching any of this:
**mutation handlers must copy only what they change.** Both bugs found in this
audit were, at bottom, writes that fired when nothing had really changed — the
same class of problem that invariant exists to prevent. `updateTask` now sets
`completedAt` only on a real transition, and `moveTask` declines a move that
cannot change anything. If you add a handler that touches tasks, check it
against that rule before checking it against anything else.
